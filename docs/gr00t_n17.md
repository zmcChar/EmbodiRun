# GR00T N1.7 HF and vLLM-Omni integration

The model name used by this repository is `gr00t_n17`; the upstream checkpoint
is `nvidia/GR00T-N1.7-3B`.

## Runtime boundary

Both providers share `Gr00tN17Adapter` and its canonical nested
`video/state/language -> named action mapping` contract:

```text
                              ┌─ HF: Engine → TorchCudaBackend → Gr00tPolicy
RawRequest → Gr00tN17Adapter ─┤
                              └─ vLLM-Omni: OpenPI → native GR00T pipeline
```

The Omni service is a remote inference endpoint, not a hardware
`BackendSession`. Treating it as a backend would create two schedulers and
would not satisfy the backend's per-entrypoint contract.

The first slice supports only
`OXE_DROID_RELATIVE_EEF_RELATIVE_JOINT` and eager execution. Its synthetic
smoke request contains two RGB streams, state, and one language instruction.
The expected named actions are `eef_9d [40,9]`,
`gripper_position [40,1]`, and `joint_position [40,7]`.

## Prerequisite: gated Cosmos backbone

GR00T N1.7 loads `nvidia/Cosmos-Reason2-2B`. The Hugging Face account used by
the process must accept that model's NVIDIA license and contact-sharing form,
then authenticate locally:

```bash
hf auth login
```

Accept access at:

<https://huggingface.co/nvidia/Cosmos-Reason2-2B>

Downloading only the public `GR00T-N1.7-3B` checkpoint is insufficient.
`local_files_only` in this integration controls resolution of the outer GR00T
snapshot; NVIDIA's current policy resolves its nested Cosmos dependency
independently.

vLLM-Omni 0.24.0 additionally uses the processor from
`Qwen/Qwen3-VL-2B-Instruct`; it does not need that model's weights. Cache the
processor files before an offline launch:

```bash
hf download Qwen/Qwen3-VL-2B-Instruct \
  chat_template.json config.json generation_config.json merges.txt \
  preprocessor_config.json tokenizer.json tokenizer_config.json \
  video_preprocessor_config.json vocab.json
```

## Run

NVIDIA's current reference repository requires Python 3.12 and pins its own
Torch/Transformers stack. Keep it isolated:

```bash
git clone https://github.com/NVIDIA/Isaac-GR00T.git
cd Isaac-GR00T
git lfs install
git lfs pull
uv sync --python 3.12
uv pip install -e /absolute/path/to/RLinf-deploy --no-deps

uv run python /absolute/path/to/RLinf-deploy/examples/gr00t_n17.py \
  --provider hf \
  --checkpoint nvidia/GR00T-N1.7-3B \
  --device cuda:0 \
  --allow-download
```

The adapter loads the official policy on CPU and exposes `policy.model` as the
package runtime module. `TorchCudaBackend` owns placement on the selected GPU.
The complete policy includes NumPy preprocessing and CPU action decoding, so
this path intentionally rejects whole-policy `torch.compile`.

## vLLM-Omni provider

GR00T is available natively in vLLM-Omni 0.24.0. Keep vLLM and vLLM-Omni in
their own Python 3.12 environment and use identical versions:

```bash
uv venv --python 3.12 .runtime-envs/vllm-omni
uv pip install \
  --python .runtime-envs/vllm-omni/bin/python \
  "vllm==0.24.0" \
  "vllm-omni==0.24.0" \
  "transformers==5.8.1" \
  --torch-backend=auto

OMNI_CONFIG=$(
  .runtime-envs/vllm-omni/bin/python -c \
  'from importlib.resources import files; print(files("vllm_omni") / "deploy" / "Gr00tN1d7.yaml")'
)

CUDA_VISIBLE_DEVICES=0 \
VLLM_WORKER_MULTIPROC_METHOD=spawn \
HF_HUB_OFFLINE=1 \
TRANSFORMERS_OFFLINE=1 \
.runtime-envs/vllm-omni/bin/vllm serve /path/to/GR00T-N1.7-3B-snapshot \
  --omni \
  --deploy-config "$OMNI_CONFIG" \
  --host 127.0.0.1 \
  --port 8000 \
  --served-model-name gr00t-n1d7 \
  --init-timeout 1200 \
  --stage-init-timeout 900 \
  --disable-log-stats
```

From a client environment:

```bash
python -m pip install -e '.[gr00t_client]'
python examples/gr00t_n17.py \
  --provider vllm-omni \
  --url ws://127.0.0.1:8000/v1/realtime/robot/openpi
```

`--stage-configs-path` still accepts the bundled YAML in 0.24.0, but
`--deploy-config` is the current interface. `--gpu-memory-utilization` is not a
hard cap for this custom diffusion path; the native implementation loads the
complete BF16 policy on the selected GPU.

## RTX 5080 verification

Both paths were verified on 2026-07-29 with one RTX 5080 (16,303 MiB), the same
local checkpoint, and the same synthetic DROID request:

| Provider | Runtime | Setup/startup | One request | Whole-GPU memory |
| --- | --- | ---: | ---: | ---: |
| `hf` | Torch 2.9.0+cu128, Transformers 4.57.3 | 37.74 s | 1.04 s | 8,764 MiB |
| `vllm-omni` | vLLM/vLLM-Omni 0.24.0, Torch 2.11.0+cu130 | 12.56 s | 1.55 s | 8,379 MiB |

These numbers are a correctness smoke measurement, not a throughput benchmark.
The desktop used approximately 2.1 GiB in both samples. Both providers returned
`eef_9d [40,9]`, `gripper_position [40,1]`, and
`joint_position [40,7]`.
